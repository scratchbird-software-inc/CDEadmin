*****************************************
BI dashboards: the editor and viewer UI
*****************************************

Stream C, dashboard UI slice. The backend is described in
:doc:`bi_dashboards`; this page covers the front end, which extends the BI
questions tool (:doc:`bi_query_builder_ui`) rather than adding a parallel one.
It lives in ``cdeadmin_ui/modules/bi/``, is reached from the same
``bi.questions`` surface, and talks to the endpoint only through the
``bi_dashboard_*`` workspace actions. There is no new panel in
``ProviderWorkspaceContent.jsx`` and no engine branch in React.

Collection tree
===============

The tree lists dashboards beside questions (``DashboardList.jsx``). Each row
offers open (viewer), edit, rename, move, archive or restore, and duplicate,
using ``bi_dashboard_update``, ``bi_dashboard_move``, ``bi_dashboard_status``
and ``bi_dashboard_clone`` with ``expected_revision``. Search covers questions,
dashboards and collections. **New dashboard** and **Import monitoring
dashboard** sit beside **New question**.

Editor
======

``DashboardEditor.jsx`` edits the stored document exactly as
``dashboard_models.validate_dashboard`` defines it (``contract_version``
1.0.0, 24 column grid). The draft is held by the pure reducer in
``dashboardState.js``; ``toDashboard(fromDashboard(x))`` is the identity on a
backend normalised document, which a Jest spec checks against fixtures
generated by ``tools/tests/fixtures/cdeadmin_bi/generate_dashboard_ui_fixtures.py``
from the real validators.

* Layout: ``LayoutGrid.jsx`` is a small CSS grid (no layout dependency). Each
  card has Move and Resize handles: drag with the pointer, or use the arrow
  keys (Move moves, Resize or Shift resizes, one cell per press). Moves push
  overlapping cards down (``dashboardLayout.js``); changes are announced.
* Cards: add a question card through the picker (search, latest or pinned
  revision), or a text card. Text is Markdown rendered by ``markdown.js`` into
  React elements; raw HTML is shown as text and only http, https and mailto
  links survive. Each card has a title, a tab and a visualization override.
* Tabs: add, rename, remove (removing a tab removes its cards and every filter
  mapping, cross-filter and drill-through that used them).
* Filters: text, number, date range, select and multi select, with default and
  required flag. The mapping grid lists every question card per filter, maps
  it to a parameter or a field, and flags unmapped cards and rules the server
  would reject (``check_mappings``).
* Interactions: cross-filters and drill-throughs (question or dashboard
  target, ``column`` or ``row`` trigger, ``column``, ``value`` or ``filter_id``
  sources) are edited in a side panel in the exact schema shape.
* Checks: errors and warnings are summarised above the grid.

Viewer
======

``DashboardView.jsx`` runs the cards of the visible tab through
``bi_dashboard_card_run`` with at most four in flight
(``dashboardViewer.js``). Each card has its own loading, error and stale state
and keeps its previous result, flagged stale, when a rerun fails or filters
change. The result cache is honoured: a cached result shows "Cached at" and
the per-card **Refresh** and **Refresh all cards** use ``bypass_cache``. The
auto-refresh interval reruns without bypassing the cache. The filter bar
commits its drafts with **Apply filters**; required filters without a value
hold the cards back. Clicking a cell or chart mark asks the server
(``bi_dashboard_cross_filter`` or ``bi_dashboard_drill``) what to do; the
viewer keeps the returned filter values and exclusions. A question drill opens
the target with the returned parameters, a dashboard drill opens the target
dashboard; a breadcrumb leads back. Cards open full screen.

Save, revisions and the unsaved guard
=====================================

Save sends ``expected_revision``; a conflict offers **Reload latest**. History
(``bi_dashboard_history`` and ``bi_dashboard_revision``) restores a revision as
an unsaved draft. The guard in ``BIQuestionsTool.jsx`` stores the blocked
action as plain data (an intent such as ``openDashboard``) and performs it from
``perform(intent)`` after **Discard changes**; no function is kept in React
state. ``DashboardTool.spec.jsx`` checks that no ``bi_dashboard_get`` is issued
while the dialog is open and that **Keep editing** keeps the draft.

Monitoring dashboards
=====================

**Import monitoring dashboard** takes a ``dashboard.ddn`` file or a
``ddn-source-workspace@1`` snapshot (``.json``), calls
``bi_dashboard_from_ddn`` and opens the result in the same editor and viewer as
an unsaved draft, with the conversion loss report.

Tests
=====

Specs in ``web/regression/javascript/bi/``: ``dashboardLayout``,
``dashboardState`` (round trip, cascades, mapping, cross-filter, drill),
``dashboardViewer`` (reducer, bounded concurrency, drafts, markdown, import
input) and ``DashboardTool`` (component tests with a fake backend: list
actions, guard, editor, viewer, cross-filter, history, import).

Known gaps
==========

* Monitoring import is file based; the published monitoring draft is not
  fetched through the per-engine definition route.
* Chart series colours are not theme tokens (a pre-existing chart wrapper
  gap), and chart marks need the **Show data** table for keyboard use.
* The viewer shows the latest saved revision only.
* Semantic field suggestions depend on the model being loaded.
* MySQL still has no descriptor entry (:doc:`bi_ui_mysql_handoff`).
* No live database test.
